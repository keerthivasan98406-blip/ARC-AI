## Approach

The repository uses a **two-layer configuration system** split between the Node.js backend and the Vite/React frontend:

- **Backend (Node/Express)**: `dotenv` is loaded at startup from `server/.env`, and values are read via `process.env`. There is no central config module — each value is consumed inline where needed.
- **Frontend (Vite + React)**: Build-time env vars are loaded via Vite's `loadEnv(mode, '.', '')` in `vite.config.ts`. Only variables prefixed with `VITE_` are exposed to the browser through `import.meta.env`. A single variable (`VITE_OPENROUTER_API_KEY`) is additionally re-exposed via `define` as a global `import.meta.env.VITE_OPENROUTER_API_KEY` for compatibility.

There is no runtime feature-flag framework, no YAML/TOML config loader, and no centralized settings object. Configuration is purely file/env-based.

## Key Files

- `server/.env` — runtime secrets for the Express server (`PORT`, `AICC_API_KEY`, `GROQ_API_KEY`).
- `vite.config.ts` — loads env via `loadEnv`, defines build output, dev proxy, and injects `VITE_OPENROUTER_API_KEY` into `import.meta.env`.
- `vite-env.d.ts` — TypeScript declaration for `ImportMetaEnv.VITE_OPENROUTER_API_KEY`.
- `services/databaseService.ts` — reads `import.meta.env.VITE_API_URL` (fallback `http://localhost:5000/api`).
- `services/geminiService.ts` — reads `import.meta.env.VITE_API_URL` (fallback `/api`).
- `server/index.js` — loads `.env` via `require('dotenv').config({ path: ... })` and consumes `process.env.PORT`, `process.env.AICC_API_KEY`, `process.env.GROQ_API_KEY`.
- `plant-disease-detector/backend/.env.example` — example env template for the sub-project.
- `tests/verify-env.js` — helper that checks whether `VITE_API_URL` is set in the process environment.

## Architecture & Conventions

1. **Environment files live next to the code that consumes them.** The only `.env` committed to the repo is `server/.env`; there is no root-level `.env`. The sub-project under `plant-disease-detector/backend/` ships a `.env.example` instead of a real `.env`.

2. **Secrets vs. public config are distinguished by prefix:**
   - Backend secrets use plain names (`PORT`, `AICC_API_KEY`, `GROQ_API_KEY`) and are accessed via `process.env`.
   - Frontend-visible config uses the `VITE_` prefix (`VITE_API_URL`, `VITE_OPENROUTER_API_KEY`) and is accessed via `import.meta.env`.

3. **Fallback defaults are baked into the consuming code**, not in the env file. Examples:
   - `server/index.js`: `const PORT = process.env.PORT || 5000;`
   - `server/index.js`: `const AICC_API_KEY = process.env.AICC_API_KEY || 'sk-LmeoayPMfQIrDyuRJmZPmvI9L1VkFY9pAXWSBhE42yMuPxPM';` (a hardcoded fallback key).
   - `services/databaseService.ts`: `const API_URL = import.meta.env.VITE_API_URL || 'http://localhost:5000/api';`
   - `services/geminiService.ts`: `const API_URL = import.meta.env.VITE_API_URL || '/api';`

4. **Build-time injection for one special var:** `VITE_OPENROUTER_API_KEY` is explicitly mapped in `vite.config.ts` via the `define` block so it is available as `import.meta.env.VITE_OPENROUTER_API_KEY` even though it is not auto-injected by Vite's default `VITE_` prefix handling.

5. **Dev proxy replaces the need for a separate frontend API URL:** During development, `vite.config.ts` proxies `/api` to `http://127.0.0.1:5000`, so `geminiService.ts` can call `/api/chat` directly without setting `VITE_API_URL`.

6. **TypeScript types for env vars are declared manually** in `vite-env.d.ts` rather than generated by a tool.

7. **No validation or schema enforcement exists** for any env file. Missing keys fall back to defaults or empty strings (e.g., `GROQ_API_KEY` falls back to `''`).

8. **Deployment configuration is external to the app code:** `render.yaml` and `netlify.toml` (in the sub-project) describe deployment targets but do not define application configuration.

## Conventions & Constraints

- **Backend env loading**: `server/index.js` calls `require('dotenv').config({ path: path.join(__dirname, '.env') })` at startup, so the server always reads `server/.env` specifically (not the repo root `.env`).
- **Frontend env exposure**: Only variables with a `VITE_` prefix are available in the browser bundle via `import.meta.env`. This is enforced by Vite's `loadEnv` behavior used in `vite.config.ts`.
- **API URL convention**: Frontend services expect `VITE_API_URL` to point at the backend; if unset they default to `http://localhost:5000/api` (database service) or `/api` (Gemini service).
- **Hardcoded fallbacks**: Several secrets have inline fallbacks in source code (`AICC_API_KEY` has a literal key string; `GROQ_API_KEY` falls back to `''`). This means the app can run without an env file, but may silently use a non-secret default.
- **No env validation**: There is no startup check that enforces required variables. `tests/verify-env.js` is a manual diagnostic script, not part of the app's runtime.
- **No shared config module**: Each consumer imports env directly; there is no `config/` directory or centralized settings loader.
- **Sub-project isolation**: The `plant-disease-detector/backend/` sub-project has its own `.env.example` and does not share the root server's env.
